# Hand over what the code cannot say

The handover you already have — purpose, build/run/test, architecture layers, invariants with the test enforcing each, working method, landmines, demo accounts, walkthrough, open work with owners, where to work per area — covers the content that every practitioner checklist converges on, and it already contains the single most underused field in the literature: the test that confirms each invariant, which [MADR](https://adr.github.io/madr/) calls **Confirmation** and recommends implementing in Java as an ArchUnit test. What it is missing is not a section but three categories of content: **provenance** (what was rejected and why, which only an append-only decision log can hold), **deliberate omissions** (a non-goal and a bug look identical to a cold reader), and **everything that is not in the clone** — and in this repository that last gap is literal, because the root `HANDOVER.md` that carries the toolchain facts, along with every file it links to, is excluded by `.gitignore`. The evidence base behind all of this is sharply asymmetric and the asymmetry should drive how much effort each recommendation gets: documentation *quality* has large measured effects ([DORA](https://dora.dev/capabilities/documentation-quality/)), code-comment drift has a measured floor of **11%** ([DocPrism](https://arxiv.org/abs/2511.00215)), coverage-as-quality-target is measurably wrong ([Inozemtseva & Holmes, ICSE 2014](https://cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)), and agent context files have exactly one controlled study, whose result is deflationary — about **+4 percentage points on average and no gain at all for Claude Code** ([arXiv:2602.11988](https://arxiv.org/html/2602.11988v1)). Meanwhile hazard documentation, repository hygiene, ADR longevity and staleness tooling have **no measured evidence whatsoever**. The practical consequence for a single developer with 231 main sources, 362 tests and no CI is that most of the recommended work is a one-off pass whose output is a dated baseline, and only two things are worth automating.

## The nine sections are right; provenance, non-goals and the unclonable are what is missing

The convergent core of every software-specific handoff checklist is narrower than most templates: get the thing building and testing from a clean machine, inventory everything that lives outside version control, and record the *why*. [Simple Thread's checklist](https://www.simplethread.com/handing-off-a-software-project/) has nine items and names the dominant failure mode precisely — receiving teams burn their first days on "software archaeology" merely to compile the software and run the tests, because nobody has set the project up from scratch recently, so hidden problems surface exactly at handover. The same source calls **access to the previous engineer the most critical asset**, which is the one thing a cold pickup cannot have; the document's job is therefore to carry precisely what that person would have supplied — rationale, workarounds, hazards — and not structure, which a competent reader derives from the code. [EngThrive's industrial report](https://arxiv.org/pdf/2605.04259) on an organisation of roughly 4,000 developers points the same way from the other end: assigning a trivial first pull request improved Time-to-First-PR by **30%** and those hires made **23% more pull requests over twelve months** than controls, and the paper notes the first PR is mostly about getting the environment working.

Against that, the first genuine omission is a **decision log that records rejected alternatives**. [Nygard's 2011 ADR format](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions) — Title, Context, Decision, Status, Consequences, one or two pages, written as a conversation with a future developer — is motivated by exactly the cold-pickup problem: a newcomer who finds an unexplained decision can either accept it without understanding it, which is risky if the context has changed, or reverse it without understanding it, which may quietly destroy value the decision protected, such as an untested non-functional requirement. Nygard argues a project that accumulates enough unexplained decisions ends up with developers afraid to change anything. The structural point, and it is the strongest argument in this whole report, is that **an ADR is the one documentation genre immune to staleness by design**: it is a dated record of a past decision, so it never needs updating, only superseding with [MADR's](https://adr.github.io/madr/) `status: superseded by ADR-0123`. A handover document describes current state and decays continuously; an ADR log is append-only. A handover that restates decisions duplicates; one that indexes them does not. The counterweight is real: the research base is thin and short-horizon — a Chalmers action-research study introduced Markdown ADRs at one company for **two months** and reports benefits as team *perceptions* rather than measurements, while noting there is little empirical evidence on how ADRs are used in practice ([Chalmers](https://research.chalmers.se/en/publication/538920)) — and an IBM team that tracked ADRs for over two years concluded that **not every decision should become an ADR** ([InfoQ](https://www.infoq.com/articles/architectural-decision-record-purpose)). Write them only for decisions that were genuinely contested. The dominant practitioner failure mode is enthusiastic adoption followed by quiet abandonment ([DEV](https://dev.to/jonoherrington/how-to-write-architecture-decision-records-that-actually-get-used-4i2), explicitly labelled "composite practitioner data", i.e. anecdotal).

The second omission is **deliberate non-doing, recorded as such**. Standard design-doc practice has a Non-goals section whose stated purpose is to name what a proposal will not address ([Pragmatic Engineer](https://blog.pragmaticengineer.com/rfcs-and-design-docs/)), and MADR's status vocabulary includes **rejected** — a decision deliberately not taken, recorded rather than deleted. This matters for a cold pickup in a specific way: an undocumented deliberate omission is indistinguishable from a bug, so a new maintainer or a fresh agent will "fix" it, which is the same failure Nygard describes for silently reversed decisions. The third omission is **the state model for open work**. Your handover lists open items with who each waits on, which is already ahead of most templates; what the conventions add is the discipline that an open item must be **phrased as a question someone can answer, not as a topic** — the guidance is explicit that "Thoughts?" does not guide a reviewer and that each entry should be a specific, answerable question ([dev.to](https://dev.to/pixari/writing-better-rfcs-and-design-docs-20pj)) — plus a fourth state most lists lack: deferred with a revisit trigger, which is what MADR's **More Information** section is for. A four-state scheme (ready to start / blocked on a decision, as a question with a named decision-maker / deliberately not done / deferred with a trigger) is assemblable from these conventions but **no source presents it as a framework, and no established practice distinguishes "waiting on the business" from "ready to code"** — that scheme is an inference, not sourced practice.

The fourth omission is **everything outside the repository**, and here the research note's abstract point becomes a concrete finding about this project. `.gitignore` excludes `PRD.md`, `PHASES_AND_TASKS.md`, `ASSIGNMENT_AND_DOCS_BRIEF.md`, `.agents/`, `graphify-out/`, `research_notes/`, `/data/`, `exports/`, `logs/`, `.runtime/` — and `/HANDOVER.md`. The tracked `docs/HANDOVER.md` (259 lines) and `docs/TASKS.md` survive a clone; the 22-line root `HANDOVER.md` does not, and it is the only place that carries the operationally decisive facts: that `JAVA_HOME` must be exported to `.runtime/jdk-17/Contents/Home`, that this path is **a symlink into a disposable tool cache that can disappear**, that the wrapper downloads Maven 3.9.9 into `~/.m2/wrapper` on first use, that a full `./mvnw clean verify` takes **about eleven minutes**, that four display-dependent test classes skip themselves headlessly, that one 50,000-package load test runs only on request, and that the checkout holds live workspace data so a clean install must be rehearsed elsewhere. Every link in that file — to `.agents/archive/HANDOVER-2026-11-24.md`, to the assignment brief, to the PRD, to the phase log — is a dangling reference for anyone who receives the repository rather than the laptop. That is the archaeology failure in advance. The fix is not to track everything; it is to decide, per artefact, whether a successor needs it, and to move the toolchain block into the tracked document. The credential rule from the same literature stays: accounts and assets get inventoried in the document, but secrets are referenced via a vault and **never inlined** ([dev.to IT handover template](https://dev.to/automatehq/the-it-project-handover-checklist-that-prevents-disasters-free-template-inside-1gkj)).

Three smaller additions are each cheap and each sourced. A **per-document last-reviewed date and a named owner**: Google's freshness dates and "Last reviewed by <owner>" byline measurably increased adoption, and in the GooWiki deprecation **about 90% of documents had had no views or updates in the prior few months** — the best available evidence that an unowned, unreviewed document is dead weight regardless of content ([Software Engineering at Google, ch. 10](https://abseil.io/resources/swe-book/html/ch10.html)). A **reflective closing artefact**: Greg Wilson's succession chapter asks for what you learned, what you would do differently, *and* what you accomplished — not only the regrets — and specifies a two-part succession plan separating final state from transition ([Third Bit](https://third-bit.com/closure/handover/)). And a **"how to read this history" note**: with 99 commits whose subjects are descriptive prose rather than conventional-commit prefixes, the convention is legible but non-mechanical, and stating it explicitly costs a sentence and saves a successor from guessing. Wilson also supplies the strongest argument for making the document self-sufficient: a successor six weeks into one of his gradual handovers took a job whose contract barred outside open-source work.

Finally, the acceptance test. Rather than grading the document against a section list — for which **no study ranks handover sections by measured usefulness to recipients**, so all ordering claims in this area are practitioner opinion — grade it against DORA's measured attributes: **reliable, findable, up to date, relevant**, with clarity, findability and reliability named explicitly on the capability page ([DORA](https://dora.dev/capabilities/documentation-quality/)). DORA's result is a moderator effect, not a direct one: the organisational-performance lift from each technical capability is far larger where documentation quality is above average — continuous integration **34% versus 750%**, version control **27% versus 278%**, trunk-based development **36% versus 1525%**. Documentation does not substitute for practices; it multiplies their payoff, which is the evidential case for documenting the working method and the verification loop rather than only the artefact. Two cautions the notes insist on: the **12.8x / 2.4x / 2.7x multipliers circulating in secondary summaries of the 2023 report are not the same numbers** as the capability-page lift table and the two presentations are not reconciled in any retrievable source, so the capability page is the citation to use; and the familiar onboarding benchmarks are conventions, not measurements — the 90-day figure has **no primary research behind it** ([Sourcegraph](https://sourcegraph.com/blog/developer-onboarding)), and first-commit metrics are noisy because a first commit "might be just an ad-hoc test for the user" ([arXiv:2101.08903](https://arxiv.org/pdf/2101.08903)).

## Housekeeping has a correct order, and dead code must precede mutation scores

The five areas named in the brief are not independent, and the ordering matters more than the tool choices because several steps change the inputs to the others. The defensible sequence — and it is reasoning from dependency between steps, not from measured defect-detection rates, because **no study compares the yield of these checks against each other** — is: secrets first, repository hygiene second, build reproducibility third, dead code fourth, test hygiene fifth, dependency and security snapshot last, then write the handover against what the first six actually found.

**Secrets go first** because the answer may be "rewrite history", which invalidates every commit hash anything else might reference, and because rotation is time-sensitive. The decisive mechanical detail is that a working-tree scan and a history scan are different scans: `gitleaks git` runs over `git log -p` patches and **sees only additions in history**, while `gitleaks dir` scans the working tree — so the first catches a credential committed and later deleted, the second catches an untracked or gitignored secret file sitting on disk now, and neither substitutes for the other ([gitleaks](https://github.com/gitleaks/gitleaks)). Note that `gitleaks detect` and `protect` were **deprecated in v8.19.0**, so older blog instructions are wrong, and that the README now carries a warning that the project is **feature complete** and will receive only security patches — worth knowing for a recommendation with a multi-year horizon. GitHub's guidance is unambiguous about order: **revoke or rotate first**, which may remove the need to rewrite history at all, and only then consider `git-filter-repo`, whose documented costs include changed commit hashes that break tooling, inaccessible PR diffs, and removal of commit and tag signatures ([GitHub docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)). For a single-developer repository that has never been published, rotation plus a **baseline file** recording known accepted findings (a seeded test password, say) is the honest end state; rewriting mostly buys the ability to say the history is clean, at the cost of invalidating the commit references this project's own documents contain. No empirical study of secret-leak prevalence or scanner false-positive rates was found, so there is no evidence base for how much this check is worth relative to the others.

**Repository hygiene is the least evidence-backed area in the entire topic** — no empirical research was found on the costs of gitignore correctness, large files, stale branches or commit-message quality for maintainer onboarding — and it should not be presented as evidence-based. It is also the cheapest to check and the most immediately visible. The question for this project is not whether `.gitignore` is correct but **which of `data/`, `exports/`, `logs/`, `reports/`, `.runtime/`, `graphify-out/` and `target/` are inputs, which are outputs, and which are tracked**, because a newcomer who deletes a generated directory that turns out to hold the only copy of the SQLite database has destroyed data the build cannot recreate — and the root handover already states that the checkout holds live workspace data. A one-line-per-directory table in the README answers it. A `.gitattributes` with `* text=auto` plus explicit `binary` markings matters more than usual here, because Maven's own reproducibility guide notes CRLF/LF differences as a source of output divergence and this project ships Windows, macOS and Linux launchers ([Maven guide](https://maven.apache.org/guides/mini/guide-reproducible-builds.html)).

**Build reproducibility means two separate things**, and only the first is essential. Day-one buildability is pinned Maven (done — the wrapper pins 3.9.9), pinned JDK (not done), documented prerequisites, and a verified clean-clone build. Bit-for-bit determinism is the sharper test that nothing in the build depends on the original developer's machine: "a build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies" ([Reproducible Builds](https://reproducible-builds.org/docs/definition/)). Maven's recipe is `mvn artifact:check-buildplan` to find plugins needing upgrades, then `<project.build.outputTimestamp>` in the POM, then `mvn clean install` followed by `mvn clean verify artifact:compare`, which prints a summary like "39 files ok, 18 different" and a ready-to-run diffoscope command per differing artefact. Three facts land directly on this project: reproducible mode is **on by default only from Maven 3.10.0 and 4.0.0-beta-5**, so at 3.9.9 the property must be set explicitly; **output depends on the JDK major version** used to compile, while `maven.compiler.release=17` constrains the output API and not the compiler, so a successor on JDK 25 can build successfully and produce different bytecode; and a local rebuild is **not proof**, because it can still leak the username or working directory. The gap that closes the JDK half is Maven Toolchains, with one trap worth memorising: **version matching is exact, so `17` does not match `17.0.20`** — use `[17,18)` — and Maven does not verify that a `jdkHome` really is that vendor and version, it only checks the directory exists ([Maven toolchains guide](https://maven.apache.org/guides/mini/guide-using-toolchains.html)). Two further inferences specific to this build: `distributionType=only-script` means the wrapper downloads Maven on first use, so **a successor needs network access on day one** and a corporate proxy breaks the first build; and `maven-shade-plugin` is the plugin most likely to account for the "different" files in an `artifact:compare` run, with **no published guidance found on reproducibility for shaded uber-jars** — the likeliest friction point here.

**Dead code must come before mutation testing**, so you are not scoring tests for code about to be deleted, and before the dependency snapshot, so the SBOM describes the final state. The case for removing it is about comprehension, not correctness: a TSE multi-study found dead code "significantly hampers source code comprehensibility and modifiability", especially in unfamiliar code — exactly the new maintainer's condition ([TSE 2018](https://mustang.cec.miamioh.edu/Resources/Publication/TSE18-DeadCode.pdf)) — and an industrial study of dead methods in a .NET web application found **48% of the modifications made to dead methods were unnecessary** ([Hauptmann et al., ICSE 2012](https://wwwbroy.in.tum.de/publ/papers/ICSE12Hauptmann.pdf)). The critical constraint is that static reachability analysis is reliably wrong in one direction: **published precision for class-level static dead-code detection is about 72%** ([Eder et al.](https://teamscale.com/hubfs/26978363/Publications/2014-dead-code-detection-on-class-level.pdf)), because anything reached by reflection, DI, annotation processing or a string-keyed lookup is reported as unused, and CodeQL's own Java documentation states such methods are "very hard to identify statically" ([CodeQL](https://codeql.github.com/docs/codeql-language-guides/navigating-the-call-graph)). That is why Error Prone's `UnusedMethod` restricts itself to **private** methods, on the stated reasoning that those can be safely removed without considering other source files ([Error Prone](https://errorprone.info/bugpattern/UnusedMethod)), and why ArchUnit-based unused-code rules produce false positives on **inlined String constants** ([JDriven](https://jdriven.com/blog/2021/01/Detect-delete-unreferenced-code-with-ArchUnit)). A three-filter pipeline follows — safe static pass, then a full-text grep of every candidate's simple name across resources and SQL, then a class-load trace (`-verbose:class` or a JVM agent) through the main workflows, run **against the shaded artefact** because shading can itself break reflective lookups — and every finding stays a hypothesis, not a delete list. Note the asymmetry in the evidence: **no study measures the labour cost of removing dead code**, only the cost of keeping it, so claims that removal pays for itself in developer time are unsupported. The i18n keys in `src/main/resources/i18n/translations.csv` are the inverse problem and mechanically tractable by script in both directions (unused keys, missing keys), with runtime-concatenated keys as the known failure mode — but **no published tool or study specific to unused i18n key detection in Java was found**, so that is an inference, not sourced practice.

**Test hygiene is where the strongest measured finding in housekeeping lives, and it is a negative one.** Inozemtseva and Holmes generated **31,000 test suites across five large Java systems** and, once suite size was controlled for, found the correlation between coverage and effectiveness **low to moderate**, with stronger coverage criteria giving no additional insight; their conclusion is that coverage is useful for finding under-tested code but **"should not be used as a quality target"** ([ICSE 2014](https://cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf)). The number worth reporting at handover is therefore a mutation score, not a coverage percentage, because mutation testing is the only check here that finds tautological tests — a test that asserts nothing, or only re-asserts the mock it configured, cannot kill a mutant and shows up as a survivor in otherwise "covered" code. [PIT](https://pitest.org/) runs entirely locally with no account and no CI (`mvn test-compile org.pitest:pitest-maven:mutationCoverage`), and its own documentation says plainly that line coverage "does not check that your tests are actually able to detect faults"; practical settings are `threads` (**default 1**, worth raising), `withHistory` for fast repeat runs, and `excludedMethods`. Google's experience is the configuration lesson: mutation testing became viable by **mutating only the lines changed in a diff**, and developer-driven suppression of uninteresting mutants raised reported usefulness **from 20% to 80%** ([State of Mutation Testing at Google](https://research.google/pubs/state-of-mutation-testing-at-google/)) — so configure exclusions before reading the first report, or it produces a pile nobody acts on. Review-time mutation integration is the **commercial** arcmutate product; the local run is free.

Flakiness is the thing most likely to make a successor stop trusting the suite, and the figures are Google's: **about 1.5% of all test runs report a flaky result and almost 16% of Google's tests have some level of flakiness** ([Micco, 2016](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)), with a further-cited claim that **84% of pass-to-fail transitions are attributable to flakiness** rather than real breakage (citing Google data, [not an independent measurement](https://ar5iv.labs.arxiv.org/html/2112.04919)). Microsoft's study across six large proprietary projects found **asynchronous calls are the leading cause** ([Lam et al.](https://www.microsoft.com/en-us/research/?p=671544)), which maps directly onto a Swing application with a SQLite backend: tests touching the EDT, timers or background threads are the first place to look, not an even sweep. With no CI the detection has to be manual and is cheap at this size — run the suite ten to twenty times back to back and diff, then once with Surefire's `runOrder=random` to expose order dependence, then once with `-DforkCount=1 -DreuseForks=false` versus the default to expose state surviving between classes in the same JVM. The defensible move for a flaky test covering something real is **quarantine, not deletion**: tag it, exclude it from the default run with a documented profile, and record why — Google's practice of rerunning only tests already marked flaky is the precedent for making flakiness an explicit recorded property rather than an ambient retry policy. **No source quantifies how often a quarantined test later turns out to have been catching a real bug; Google explicitly said it does not track this.** Two things belong in the handover as measurements rather than claims: the `mvn test` wall-clock time (the root handover already records about eleven minutes for `clean verify`, which sets the successor's whole iteration loop) and the slowest tests from the Surefire reports.

**The dependency and security snapshot goes last** and all of it runs locally and free. `cyclonedx-maven-plugin` produces the SBOM, with one default worth knowing: **`includeTestScope=false`**, so the default BOM describes what ships, not what builds ([CycloneDX](https://github.com/CycloneDX/cyclonedx-maven-plugin)). Because the SBOM carries per-component licence data, it doubles as the licence inventory at this scale and no separate tool is strictly needed. [OWASP Dependency-Check](https://jeremylong.github.io/DependencyCheck/dependency-check-maven/index.html) finds known vulnerabilities, with the operational caveat that the first run "may take 20 minutes or more" and later updates take seconds only if run at least every seven days — which means **a tool run once at handover will be slow again whenever the successor next runs it**, a fact to write down. An NVD API key is free from NIST and matters a lot: **5 requests per rolling 30-second window without one versus 50 with** ([NVD](https://nvd.nist.gov/developers/start-here)). `dependency:analyze` classifies dependencies as used-and-declared, used-and-undeclared and unused-and-declared, and its analyser works **at bytecode level**, which is the documented source of its false positives — `<usedDependencies>` exists explicitly "to override incomplete result caused by bytecode-level analysis" ([Maven](https://maven.apache.org/plugins/maven-dependency-plugin/analyze-mojo.html)). For this POM that is not hypothetical: `sqlite-jdbc` and `logback-classic` are exactly the runtime and reflective cases the plugin gets wrong. `versions:display-dependency-updates`, `display-plugin-updates` and `display-property-updates` are the read-only audit goals, and the third is the relevant one here because this project's versions all live in `<properties>`. Dependabot is a GitHub-hosted service, not a local tool, so it belongs in future work rather than the pre-handover pass. Two gaps to respect: **no source gives a false-positive rate for Dependency-Check**, and the NTIA minimum SBOM elements could not be extracted from the primary PDF — anyone citing them should read [NTIA's report](https://www.ntia.gov/report/2021/minimum-elements-software-bill-materials-sbom) or the 2026 CISA guidance directly, and the [CISA page](https://www.cisa.gov/sbom) references a 2026 update whose content could not be fetched.

## Only change-coupled checks keep documentation honest; stamps inform, they do not detect

The measured literature on drift is confined to code-comment and docstring inconsistency, and the best recent multi-language measurement is [DocPrism](https://arxiv.org/abs/2511.00215), which found documentation that actively contradicts the code in **11% of developer-written code-documentation pairs** across Python, TypeScript, C++ and Java, described as a conservative lower bound. Two things follow, and both are load-bearing. First, **that 11% is a snapshot, not a rate** — it says how much is already wrong, nothing about decay speed, so any claim of the form "docs go stale within N weeks" is unsupported by the literature. There is **no measured answer at all** for prose and architecture documents, and the widely circulated cost figures (5.3 hours per developer per week, $62,000 annually, "73% of teams fail") are vendor-blog numbers with no traceable primary source and **should not be used**. Second, the measured decay mechanism is **per-change, not per-calendar-period**: inconsistency enters at a code change whose author did not touch the adjacent prose, and a 2024 study reports bug introduction is **highest immediately after an inconsistency is introduced**, diminishing over time ([arXiv:2409.10781](https://arxiv.org/abs/2409.10781v1)). That is a direct argument for change-coupled defences over time-based sweeps. (Older co-evolution figures — 97% of comment changes in the same revision as the code change — appear only in search summaries of [the Wen et al. line of work](https://www.inf.usi.ch/faculty/lanza/PUBS/P/Wen2019a.pdf) and were not verified against the primary papers; treat them as unverified.)

The same paper carries a warning that bears directly on how this project works: naive LLM prompting flags **over 90% of functions as inconsistent (98% in the ablation)** because it treats normal abstraction gaps as errors, and the constrained method only reaches a flag rate of 14–17% at precision 0.63. An ad-hoc "ask the model to audit my docs" step is therefore close to useless without that kind of filtering — it will cry wolf on nearly everything.

What genuinely holds are the techniques where the documented artefact *is* the executed artefact. In descending order of payoff per unit of effort for a Java 17 / JUnit 5 project with no CI: **JUnit tests that assert documented figures against reality** (count the CSV rows, the entity classes, the translation keys, parse the number out of the Markdown and compare) — cheap, hard verdicts, and they catch the rot type that most embarrasses a reader; **ArchUnit rules encoding the layering the architecture document claims**; and `@snippet`-backed examples where examples exist (Java 18 added the JavaDoc `@snippet` tag, which pulls example code from external source files so examples compile and can be tested with the normal toolchain — [Morling](https://morling.dev/blog/executable-javadoc-code-snippets)). [ArchUnit](https://www.archunit.org/userguide/html/000_Index.html) has three features that matter disproportionately for one person adopting it mid-project. `.because("...")` appends the rationale to the rule text so a failure reads as the documentation sentence plus the offending class and line number. `FreezingArchRule.freeze(rule)` records current violations to a plain text file in the repo, reports only new ones, and prunes fixed ones so they cannot regress — which is the difference between adopting it and not, because the realistic alternative to "fix 200 violations now" is "don't adopt". And `failOnEmptyShould` defaults to failing a rule whose should-clause receives no classes, which is **the anti-theatre mechanism**: the classic failure of architecture tests is a rule that passes because a package rename left it matching nothing. Any hand-written doc-assertion test needs the same property — a test asserting that a figure in a document matches the code must **fail, not pass, when it cannot find the figure**. The honest caveat is that there is **no measured evidence that executable docs or architecture tests reduce drift or onboarding time**; the mechanism is sound (a false claim becomes a failing test) but the outcome is unmeasured, and every claim in that direction is a blog post.

Staleness detection splits into two families with very different value here. Time-based review stamps genuinely need a scheduler to function as detection. Microsoft's HVE-core policy is the best-documented concrete instance — required frontmatter, a **90-day threshold on `ms.date`**, contributors expected to bump the date whenever they *review* a file, a weekly Monday scan opening at most one issue per stale file — and it also documents its own loophole: **"files without `ms.date` are not counted as stale"**, so a malformed date hides a stale file ([Microsoft HVE-core](https://microsoft.github.io/hve-core/docs/contributing/documentation-maintenance)). That loophole is the transferable lesson rather than the policy: **any staleness check must fail closed — missing stamp means stale, not skipped** — and so must the check's own coverage, since a freshness script that silently excludes a directory is worse than none. Without a scheduler, a `last-reviewed` stamp is still worth having as *information for the reader*, which is itself a form of honesty: a document stating the date it was last verified is less misleading than one silently implying currency. Cloudflare's two-field split is the right data model and costs nothing — last-changed comes free from git, so only `last-reviewed` needs to be in frontmatter ([Cloudflare](https://developers.cloudflare.com/style-guide/documentation-content-strategy/component-attributes/last-updated/index.md)). The change-based half is the part worth building locally: GitLab runs **`lychee --offline --include-fragments doc`** to check internal links including anchors with no network, alongside Vale for content and markdownlint for structure ([GitLab](https://docs.gitlab.com/ee/development/documentation/testing/)), and a JUnit test that resolves every file path and fully-qualified class name mentioned in the docs turns "docs reference moved code" into a red test. Line-number references are the anti-pattern this makes obvious: they break silently and cannot be verified, whereas a class or method name can be resolved. CODEOWNERS is team-only and does nothing for one maintainer. Vale is advocacy as a prose-quality tool, but a genuine mechanical check as a **terminology-consistency** tool — which matters here, given a Hungarian document set alongside English ones. None of the policy sources is an evaluation: **no measured evidence exists that staleness stamps or linters improve documentation accuracy.**

Two structural points close this out. The generated-versus-handwritten decision rule is to **generate anything that is a faithful projection of a machine-readable source** (database schema from the schema, module graph from the POM or bytecode, API reference from JavaDoc, any count from the data) and **hand-write anything that expresses intent** (why these boundaries, what the system is for, what was rejected) — the failure mode of auto-generated architecture diagrams being that they attempt the second with tools that can only do the first, showing "what exists, not what matters" ([DEV](https://dev.to/uxxu/your-c4-diagrams-are-lying-to-you-and-ai-coding-is-making-it-worse-2198)), a criticism Simon Brown extends to AI-generated C4 diagrams exhibiting "exactly the same problems as hand-drawn ad hoc diagrams" ([Brown](https://www.patreon.com/posts/151861351)). A generated artefact stays honest only if regeneration is part of the build and the committed copy is diffed against a fresh one, approval-test style; **a generated diagram committed once and never regenerated is strictly worse than a hand-drawn one, because its machine-made appearance invites trust it has not earned.** ArchUnit can invert the direction entirely by taking a PlantUML component diagram as the *source* of enforceable rules, making the picture the thing tested — the most interesting option in this area for a Java project, with **no experience reports found on how well it works in practice**. And for the bilingual problem, the settled localisation practice is to record in the derived document the **source revision it was last reviewed against**, because edit dates are a weak signal — a translation can be freshly edited and still describe old behaviour ([Microsoft Developer Community](https://techcommunity.microsoft.com/t5/microsoft-developer-community/rethinking-documentation-translation-treating-translations-as/ba-p/4491755)). MDN contributors go further and propose counting **commits** to the source rather than elapsed time ([MDN](https://github.com/mdn/mdn-community/discussions/129)), which needs no infrastructure at all: `git log --oneline <source-commit>..HEAD -- docs/Source.md | wc -l` answers "how far has the source moved since I last reviewed this". That the MDN frontmatter key remains a *proposal* and was not confirmed as shipped is part of the picture. One measured-ish finding underpins all of this: an ECSA 2024 action-research study found **"the decision on where documentation is stored has a massive influence on its perceived usefulness"** ([ECSA 2024](https://conf.researchr.org/details/ecsa-2024/ecsa-2024-research-papers/9/Introducing-Architecture-Decision-Records-in-Practice-An-Action-Research-Study)), which is the nearest thing to evidence for keeping docs in the repository rather than a wiki — GitLab's own observation that wikis go stale "because they're often disconnected from the projects they support" ([GitLab](https://about.gitlab.com/the-source/platform/how-to-accelerate-developer-onboarding-and-why-it-matters/)) is practitioner assertion, and **no empirical comparison of docs-in-repo against wiki staleness was found**.

## Context files move behaviour, not capability — but handoff notes halve rediscovery

The expectation to correct first: there is exactly **one substantial controlled study** of repository context files, and its result is deflationary. [Gloaguen et al. (ETH Zurich / LogicStar, arXiv:2602.11988)](https://arxiv.org/html/2602.11988v1) ran Claude Code, Codex and Qwen Code across SWE-bench Lite (300 tasks) and a purpose-built AGENTbench (138 instances from 12 less-known Python repositories that all contain developer-committed context files), under three conditions: no file, LLM-generated, human-written. Human-written files gave **about +4 percentage points on average, with no gain at all for Claude Code**, while raising step counts by about 3.34 and cost by up to 19%; secondary coverage reports the effects as **not statistically significant** ([InfoQ](https://www.infoq.com/news/2026/03/agents-context-file-value-review/)). LLM-generated files were worse than nothing: resolution fell about **0.5% on SWE-bench Lite and 2% on AGENTbench** while cost rose **20% and 23%** and steps rose by 2.45 and 3.92; generating with a stronger model did not fix it. The authors' recommendation is blunt — omit LLM-generated context files "for now, contrary to agent-developer guidance" — which makes an **unreviewed `/init` output the single best-measured anti-pattern in this whole topic**.

Two findings inside that study are more actionable than its headline. The first is the **redundancy result**: when all documentation was removed from the repositories, LLM-generated files *improved* success by about **2.7%** and outperformed human files, which the authors read as the files mainly duplicating existing docs. That is the measured mechanism behind the weak effect, and it is the argument against merging a human handover document and an agent context file: the human document's value comes from completeness, the agent file's from omission, and the duplication is where the harm is. The second is the one **large, robust effect**, which is behavioural rather than success-rate: a tool mentioned in the context file gets used far more — `uv` appeared about **1.6 times per instance when mentioned versus under 0.01 when not, roughly 160×**. Against that, the measured null result is for overviews: LLM-generated files included codebase overviews in **100% of Sonnet-4.5 cases and 99% of GPT-5.2 cases**, and those overviews **did not reduce the steps needed before touching the files the PR changed**. Vendor guidance and independent evidence genuinely disagree here — Anthropic's blog recommends a high-level directory map ([Anthropic](https://www.claude.com/blog/using-claude-md-files)) and the ETH study found overviews bought no navigation gain — and the honest synthesis is that a map is worth at most a few lines naming non-obvious entry points, not a tree dump. The asymmetry gives a one-question test for every candidate line: **would the agent get this wrong by guessing the ecosystem default?** If no, delete it. Vaughan's version is similar — keep a line only if it is backed by a real failure, enforced by a tool, encodes a deliberate decision, or applies to a real scenario ([Vaughan](https://codex.danielvaughan.com/2026/03/27/agents-md-bloat-problem/)).

The study's limitations cut in this project's favour, and that cut is an extrapolation rather than a result. The corpus is **almost entirely Python**, which the authors note is well represented in training data, and they say context files "may matter more for niche languages and toolchains"; the dataset is small (138 AGENTbench tasks), with one sample per agent, and only task resolution was measured, not code quality or security. A Java 17 Swing desktop application with no system Java or Maven and a JDK symlink into a disposable scratch directory is precisely the case where the default ecosystem assumptions are wrong. **No study covering Java, Maven, or desktop/GUI codebases exists, and no independent replication of the ETH study was found.**

The mechanics matter as much as the content, because Claude Code's resolution rules contain a trap. AGENTS.md is read natively from **v2.1.277**, but **only when there is no `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md`** in the working directory or above it; if both exist, only the CLAUDE.md files load. The documented gotcha is that adding a `CLAUDE.local.md` for personal notes **silently stops AGENTS.md from being read** unless the project-instructions setting is switched to `claude-md-and-agents-md` ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Three further details are worth designing around: `@path` imports are **expanded into context**, so they "help you organize a long file but don't reduce its context cost" — load-on-demand needs path-scoped `.claude/rules/*.md` with `paths:` globs or skills, not imports; **HTML comments are stripped before injection**, which gives maintainer-only notes at zero token cost while remaining visible to the Read tool; and instruction files are **context, not enforced configuration** — "to block an action regardless of what Claude decides, use a PreToolUse hook instead". That last point lands on this project directly: the standing rule to run `graphify update .` before any commit is enforcement-shaped and currently lives as prose in auto memory, where it is advisory; a hook would make it a mechanism. Size guidance is **under 200 lines** on the stated grounds that longer files "consume more context and reduce adherence"; Cursor's limit is 500 lines with an explicit skip-list (don't copy style guides, use a linter; don't document common commands; reference files rather than copying them) ([Cursor](https://cursor.com/docs/context/rules)), and Copilot asks for instructions "short and self-contained" because they are sent with every chat message ([GitHub Docs](https://docs.github.com/en/copilot/concepts/response-customization)). Secrets are excluded by construction: because the file becomes part of the system prompt, treat it as documentation that could be shared publicly.

The project's current state has a gap here that mirrors the handover gap. There is **no `AGENTS.md` and no `CLAUDE.md` in the repository**; the only agent rules live in `.agents/rules/graphify.md` and `.agents/workflows/graphify.md`, and `.agents/` is **gitignored** — so a fresh session in a fresh clone receives no project instructions at all, and the user-level `~/.claude/CLAUDE.md` that currently supplies the graphify trigger does not travel with the repository. Note also that auto memory is **machine-local**, written to `~/.claude/projects/<project>/memory/`, deliberately skipping anything derivable from the codebase and anything CLAUDE.md already says, and **not a handover artefact** for anything that must survive a machine change or be reviewed. The two memory notes this project holds — the pre-commit graphify rule and the JDK-symlink toolchain quirk — are exactly the `project` category Anthropic describes as belonging in auto memory, except that the toolchain fact is something a successor on another machine must have, which argues for it being in the tracked document too.

Finally, the one place where measurement strongly supports writing something down. [Handoff Debt (arXiv:2606.02875)](https://arxiv.org/html/2606.02875) interrupted a predecessor agent at three points across 75 SWE-bench Verified tasks, giving 181 handoff points and 2,172 takeovers, holding the repository checkpoint fixed while varying only the handoff view. Success-rate gains were modest and mostly not significant (**+1.1 to +14.9 percentage points**, significant only for the weakest successor, Devstral, at +14.9 with a raw trace), but the efficiency effect was large and robust: context-bearing handoffs cut **agent events by 20–59% and prompt tokens by 42–63%**. Raw traces were most informative and most expensive; structured notes got most of the efficiency for a fraction of the prompt — for Qwen, **+4.4 points with 44% fewer events and 60% fewer prompt tokens**. The schema is worth copying because it separates mechanically derivable fields (changed source files, non-source artefacts, latest validation command and its evidence, continuation state) from judgement fields (problem understanding, work completed, observed failures, remaining uncertainty, rollback notes, recommended next action) — which means the deterministic half can be generated from `git status` and the last build output, and only the judgement half needs writing. The authors' caveat belongs in the template itself: handoff text should be treated **"as evidence to verify, not as ground truth"**, because compact notes drop exact validation commands and warnings. Two limits to keep: the successors were open-weight models (Qwen, Gemma, Devstral), **not frontier agents**, so the success-rate findings may not transfer to Claude Code, though the efficiency findings are more plausibly robust; and **a standardised in-repo handoff file is not a shipped Claude Code feature** — it remains an [open feature request](https://github.com/anthropics/claude-code/issues/11455), with community conventions diverging across `docs/tmp/handoff.md`, `SESSION_NOTES.md`, `.claude/handovers/` and others. The useful framing from that community is the one that separates the artefacts by tense: **"A transcript is history. A plan file is intent. A handoff file is continuity"** ([every.to](https://every.to/compound-engineering/guides/ce-handoff/)). **No measurement compares those placements, and no evidence exists on whether agents reliably open a human document that a context file merely names** — which is the key unknown for the whole "point, don't copy" strategy.

## Where large-organisation advice stops transferring

Almost everything in this literature that scales with headcount should be dropped, and almost everything that scales with codebase age and size should be kept. Dropped: named primary and backup owners with escalation chains; technical-writer review stages (Google scopes writers as "a limited resource" focused on cross-API work — a role with no solo analogue); the three-way split of technical, audience and writing review; audience segmentation into separate customer-facing and team-facing doc sets; ADR categorisation into subdirectories, which [MADR](https://adr.github.io/madr/) explicitly scopes to "large projects with hundreds of records", implying flat numbering is correct below that; landing-page hierarchies; CODEOWNERS; the "block the merge without docs" rule from [Write the Docs](https://www.writethedocs.org/guide/docs-as-code/), which with one maintainer and no CI degenerates into self-imposed discipline whose honest form is a pre-commit hook or a CONTRIBUTING checklist the maintainer actually runs; Dependabot, GitHub secret scanning and push protection, and arcmutate's review-time mutation testing, all of which need a hosted service or a paid account; and the inter-team cooperation benefit that both ADR studies measure, which does not transfer at all. Kept essentially unchanged: docs in source control beside the code; a clean-machine build/test/run path; flat-numbered ADRs with Nygard's five sections; MADR's Confirmation field pointing at the enforcing test; a ranked and capped hazard list; last-reviewed dates; and the inventory of things outside the repository.

Two inversions are worth stating. First, the bus-factor literature reads the opposite way for a solo project than it does for a team. [Nourry et al.](https://export.arxiv.org/pdf/2412.00313) computed the truck factor for **over 36,000 OSS projects** and titled the paper "Myth: The loss of core developers is a critical issue for OSS communities", and [Avelino et al. (ESEM 2019)](https://pure.tue.nl/ws/portalfiles/portal/128584841/ESEM2019.pdf) studied **1,932 popular GitHub projects** and found that while evolution frequently depends on a few core developers, new core developers may take over and let the project survive. For a team the lesson is redundancy; for one person there is no redundancy to build, so the only available mitigation is artefact quality, and the realistic objective is making the project **pickupable by a motivated newcomer**, not preserving the original maintainer's exact knowledge. (Wilson's one piece of direct single-maintainer guidance — keep at least two people holding each critical credential — is the exception that does need a second human.) Second, a solo project has an advantage the literature never discusses: there is no reconciliation problem between competing documents, so the single-canonical-document rule Google had to enforce organisationally is free here. The counterweight is that this repository currently has ten Markdown files under `docs/`, plus a README, plus four more planning documents at the root — which is the condition [Diátaxis](https://diataxis.fr/) was designed to resolve, and its payoff for one person is less about reader experience than about **write-once placement**: if a figure or a procedure has exactly one home, there is one place to update it. Note that Diátaxis makes **no claim about preventing rot** and has no published evidence base; its testimonials are self-reported. The structural division that follows from the sources: README for orientation plus build and run (the only document a stranger is guaranteed to open), CONTRIBUTING for the local rituals including which doc checks to run, `docs/` for Diátaxis-sorted reference, how-to and explanation, `docs/adr/` for the decision log, and the handover document as the explanation-mode narrative that **points at the others rather than restating them**. **No study compares handover outcomes between solo and team projects, and no handover template written for a single-maintainer codebase was found** — this division is assembled by inference.

**Worth automating — three things, all local.** A **gitleaks pre-commit hook**, because it is the only control in this entire list that prevents the next secret rather than finding the last one. **The figure-asserting and reference-resolving JUnit tests**, plus ArchUnit rules with `.because()` text, `FreezingArchRule` to make adoption possible mid-project, and `failOnEmptyShould` left at its failing default — these are change-coupled, which is the only defence that matches the measured per-change drift mechanism, and they run as `mvn test` with no service. And **the test suite itself staying green and fast**, since that is the successor's entire feedback loop. Add `lychee --offline --include-fragments docs` to the same local script, and a `PreToolUse` hook for the pre-commit graphify rule, which is enforcement-shaped and therefore unreliable as prose.

**Worth running once and recording as a dated baseline — everything else.** `dependency:analyze`, the vulnerability scan, the SBOM, `artifact:compare`, the mutation run, the dead-code sweep, the flakiness triage. Each produces a number or a list whose handover value is as a baseline the successor can re-derive. Wiring any of them in as a build-failing gate hands the successor a build that breaks for reasons unrelated to their change — an expiring NVD cache, a CVE published overnight, a runtime-only dependency, a new mutant — and **a failing gate the successor does not understand gets disabled, which is worse than a recorded baseline.**

**Worth deferring to when hosting exists:** Dependabot, GitHub secret scanning and push protection, arcmutate's review-time mutation testing, scheduled NVD re-scans, and any time-based documentation freshness sweep. Everything else above runs from `./mvnw` or a single local binary.

## Conclusion

The sharpest thing this research changes is where the effort should go. The intuitive model of a handover is a bigger, more complete document; the evidence points almost the opposite way. The one controlled study of agent context files found that **more content bought nothing and cost 20% more**, with the harm traced to duplicating documentation that already existed; Google's own pruning data says **about 90% of its wiki documents were unread**; and the only drift mechanism anyone has actually measured is per-change, which means calendar-based review sweeps are aimed at the wrong target. The leverage is in the *small* non-inferable facts and in the mechanisms that make a false claim fail: a toolchain block that actually travels with the clone, a Confirmation line naming the test, an ArchUnit rule that cannot silently stop checking, a count asserted rather than asserted-about. The nine sections you have are not the problem; the problem is that the most consequential paragraph in the whole set currently sits in a gitignored file.

The second shift is about what a handover is *for* when the recipient may be a model. The Handoff Debt result is the most useful number in this report precisely because it is not a success-rate claim: writing continuity down cut agent events by **20–59%** and prompt tokens by **42–63%** while barely moving whether the task got solved. For a solo maintainer paying per token and per hour of rediscovery, that is the return — not a smarter agent, a cheaper one. It also implies a different artefact shape than a document: a short structured note whose deterministic half comes from `git status` and the last build output, rewritten often, treated by its reader as **evidence to verify rather than ground truth**. Keep that separate from the human handover, keep both separate from the append-only ADR log, and the three artefacts stop competing for the same paragraph. The honest closing caveat is that none of this is well measured for a project like this one: there is no study of Java, Maven, desktop GUI codebases, or single-maintainer handovers anywhere in the sources, the hazard-documentation and repository-hygiene literature is empty, and the agent-file evidence is one Python-heavy experiment with one sample per agent. The recommendations above are therefore ordered by cost and by how directly each one converts a claim into something that can fail — which is the only quality signal available when the outcome literature does not exist.
